# テニス試合分析 フェーズ1:選手位置分析 設計書

日付: 2026-10-27
状態: レビュー待ち

## 1. 目的と背景

固定カメラで撮影したシングルスの試合映像(録画済み、約60分)から、選手のコート上の位置を取得し、軌跡・ヒートマップ・走行距離などのスタッツをレポートとして出力する。

試合分析全体は次の4フェーズに分けて、フェーズごとに「設計書 → 計画 → 実装」を回す。本書はフェーズ1のみを対象とする。

| フェーズ | 内容 | 前提 |
|---|---|---|
| 1 | コート検出・座標変換、選手検出と追跡、位置スタッツ、レポート | なし(土台) |
| 2 | ショット検出と種別(サーブ、フォアハンド、バックハンド) | フェーズ1 |
| 3 | ボール追跡・バウンド位置(イン/アウト、深さ) | フェーズ1 |
| 4 | ラリー本数、ポイント勝敗、サーブ確率 | フェーズ2・3 |

## 2. 確認済みの要件

- 入力: 固定カメラの俯瞰・後方映像。コート全体のラインが見える。録画済みの動画ファイル。
- 対象: シングルスのみ(選手2人)。
- 試合時間の目安: 60分。解像度は未確認のため 1080p と仮定する。
- 実行環境: CPU のみ(Mac を含む)。リアルタイム処理は不要。
- 出力: データ(CSV/JSON)と、ヒートマップやスタッツ表を載せた HTML レポート。PDF は任意。
- コート検出: 自動検出を採用する(ユーザー選択)。

## 3. 非目標(フェーズ1では扱わない)

- ショット検出・種別判定、ボール追跡、バウンド位置、ラリー・得点の判定。
- ダブルス対応。
- リアルタイム処理。
- 姿勢(骨格)推定。フェーズ2で追加する。
- 手持ち撮影やカメラ切り替えのある映像。

## 4. 全体構成

動画ファイルを入力すると、次の5段階を順に通ってデータとレポートを出力する。各段階は、決まった形のデータだけを次に渡す独立した部品とする。これにより、フェーズ2以降で部品を足しても既存部分を変更せずに済む。

1. 映像読み込み: 動画を5fpsに間引いて読み込む(60分で約18,000フレーム)。
2. コート検出・座標変換: ホモグラフィを推定する。
3. 選手検出・追跡: コート上の選手2人の軌跡を得る。
4. スタッツ計算: 軌跡・ヒートマップ・走行距離を実座標(メートル)で計算する。
5. レポート生成: データとレポートを出力する。

## 5. 部品の詳細

### 5.1 コート検出(部品2)

- 学習済みモデルは使わず、従来の画像処理で行う(学習データがなく、CPU で軽いため)。
- 手順:
  1. 白いライン部分を色と明るさのしきい値で抽出する。
  2. ハフ変換で直線を取り出す。
  3. テニスコートの標準寸法のモデルと照合し、ホモグラフィを RANSAC で推定する。
- コートモデルの寸法: シングルスコート 幅 8.23m、長さ 23.77m。
- 数十フレームで推定し、結果が一致するものを多数決で1つに決める。動画全体では行わない。
- 信頼度は、モデルのラインを画像に当てはめたときの一致率で数値化する。しきい値を下回れば停止して警告する。しきい値の具体値は実装時に実映像で決める。
- 確認用に、検出ラインを重ねた画像 `court_check.png` を出力する。
- 保険として、失敗時は四隅の手動指定を受け付けられる口を残す。通常は使わない。

### 5.2 選手検出・追跡(部品3)

- 軽量な人物検出モデル(YOLO nano 系)で人物を検出し、追跡(ByteTrack 系)でIDを付ける。
- 人物の足元の位置をホモグラフィでコート実座標に変換する。
- コートの外周から少し広げた範囲にいる人物だけを残す。ボールパーソンや観客は、範囲外か動きが少ないため除外する。
- 追跡IDが長く続く上位2人を選手とし、手前側・奥側に分けて選手A・Bとラベルを付ける。
- 追跡が途切れてIDが切り替わった場合は、位置の近さで同一人物につなぎ直す。

### 5.3 スタッツ計算(部品4)

- 選手ごとの走行距離、平均移動速度、前後左右の滞在割合、位置ヒートマップを計算する。
- すべてコート実座標(メートル)で計算する。
- 前後左右の割合は、サイドチェンジをまたいでも選手の傾向が打ち消されないよう、選手本人の向きを基準にする(2026-10-27 改訂)。
  - 前後: ネットからの距離で決める。前 = ネットから 6.40m 以内(`|y − 11.885| < 6.40`、サービスラインの内側)、後ろ = それより後方。
  - 左右: 選手がネットに向かって立ったときの左右。手前半分(y < 11.885)では x がそのまま(右 = +x 側)、奥半分では x を `8.23 − x` に反転してから、4.115 未満を左、それ以外を右とする。
  - 判定はサンプルごとに、そのサンプルの y で行う。コート外のサンプルも割合の計算に含める。
  - ヒートマップは変更せず、コート全体の絶対位置のまま。

### 5.4 レポート生成(部品5)

- Jinja2 で HTML を生成する。PDF は HTML からの変換で任意に出す。

## 6. 出力ファイル

| ファイル | 内容 |
|---|---|
| `positions.csv` | 時刻、選手(A/B)、コート実座標 x, y(メートル) |
| `stats.json` | 選手ごとの走行距離、平均移動速度、前後左右の滞在割合(前後はネット基準、左右は選手本人から見た向き。§5.3) |
| `heatmap_A.png` / `heatmap_B.png` | 選手ごとの位置ヒートマップ(コート図に重ねる) |
| `court_check.png` | コート検出の確認用画像 |
| `report.html` | 上記をまとめたレポート |

## 7. エラー処理

- コート検出の信頼度が低い場合は停止し、確認用画像と手動指定の案内を出す。
- 選手が2人見つからない場合は、見つかった範囲で出力して警告する。処理は止めない。
- 動画が開けない、または形式が非対応の場合は、原因が分かるメッセージで終了する。

## 8. テスト方針

- 単体テスト: 部品ごとに書く。座標変換は既知の点が正しく変換されることを確認する。走行距離は手計算できる単純な軌跡で確認する。
- 結合テスト: 短い合成映像(CG で描いたコートと動く点)でエンドツーエンドの出力を確認する。
- 実映像での精度確認: ユーザーの試合映像を1本借りて行う。自動テストには含めない。

## 9. 技術構成と前提

- Python、OpenCV、軽量検出モデル(YOLO nano 系)、追跡(ByteTrack 系)、Jinja2、pytest。
- 追跡は自作の ByteTrack 風 IoU トラッカー(等速度予測つき)を使う。supervision 0.31.2 には ByteTrack が無いため。
- 処理時間の見積もり: 5fps・約18,000フレームで15〜45分程度。これは概算で実測ではない。
- 前提: カメラはコートの後方、またはやや高い位置から、コート全体のラインが見える状態で撮影されている。ラインの一部が見えない映像では、検出が失敗する。
